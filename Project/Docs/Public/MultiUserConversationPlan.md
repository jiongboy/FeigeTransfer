## 1. 目标

在 Windows 与 macOS 客户端中提供两类可以同时使用的会话：

1. **群组会话**：最多 20 名成员（包含本机用户）共用一个群组时间线。群消息可包含文字、图片和文件。
2. **多个独立私聊**：一名用户可以同时与最多 20 个不同设备保持独立的一对一会话。私聊记录、草稿、发送状态和目标彼此隔离。

两类会话同时存在时，按完整设备身份复用到同一设备的连接。若 20 个私聊对象与一个 20 人群组的其他成员完全不同，一台设备最多需维护 39 条远端连接；若成员重叠，则只连接一次。

## 2. 首版范围与行为

| 项目 | 首版要求 |
| --- | --- |
| 平台 | Windows 与 macOS，互相兼容；同时覆盖 Windows↔Windows 与 Mac↔Mac |
| 群人数 | 最多 20 人，包含群创建者/本机用户 |
| 私聊并发 | 一名用户最多同时保持 20 个不同对象的一对一会话 |
| 共存 | 私聊与群聊可以同时在线；连接按设备身份去重并复用 |
| 拓扑 | 暂按局域网点对点全互联规划；不依赖常驻服务器 |
| 离线 | 群聊不做离线暂存或自动补投（私聊离线待发见[开发计划](CollaborationEnhancementPlan.md)）。成员离线时该成员本次未收到，状态显示未送达；用户可在成员上线后手动重发 |
| 文字 | 群聊和私聊均支持，群聊状态按成员显示 |
| 图片 | 群聊和私聊均支持，仍按原图传输 |
| 文件 | 群聊发送时向各成员分别传输；接收确认、进度、拒收和失败均按成员独立处理 |
| 失败隔离 | 某成员离线、拒绝或传输失败，不阻断其他成员或其他私聊 |
| 旧版本 | 群聊要求通信双方使用支持群组能力的版本；私聊与旧版 v3 客户端的互通策略需在协议设计阶段定稿，禁止静默降级 |

群聊文件或消息没有离线队列，表示程序关闭或对端离线期间不会替用户保管并自动补发。发送方本地历史可以记录未送达结果；手动重发时重新检查源文件仍存在且可读。

## 3. 架构基线

### 3.1 会话与连接分离

当前两端均以单一活动连接作为会话核心。新设计应把连接生命周期与会话模型分开：

- **连接管理器**以完整设备指纹为键，持有并发的已认证连接、连接状态、取消句柄与错误状态。
- **私聊会话**以对端设备指纹为键，保存该私聊的消息、草稿和界面状态。
- **群组会话**以 `groupId` 为键，保存群名、成员、成员变更版本及群消息。
- 一条设备连接可被该设备的私聊和一个或多个共同群组复用；不得因切换界面而关闭连接或把消息发往当前选中的错误会话。
- 每条连接保留一个安全握手和同意流程、一个有序写入通道及一个读取循环；并发会话不得各自抢读同一连接。

### 3.2 点对点群组投递

当前规划采用全互联点对点，不设置中心消息服务器：

- 群组成员之间需要各自建立已认证连接，20 人群组中每个成员最多连接其余 19 人。
- 发送群消息时，发送者在每条成员连接上单独加密和投递；无需设计群组共享密钥。
- 每条群消息使用唯一 `messageId`，包含 `groupId`、发送者完整指纹、消息类型和创建时间。接收方按群组与消息 ID 去重。
- 每个接收成员分别回执；发送者以成员为粒度展示送达、未送达、拒收或失败。全局状态由这些独立结果汇总，不能把部分成功显示成全部送达。
- 每个群成员发送消息时，按相同规则扇出给其他群成员。连接失败不会阻塞其余发送目标。
- 文件向每个成员作为独立传输执行，每位接收方单独批准；一个成员拒收时只结束其对应的文件传输，不影响发给其他成员的副本。

全互联能避免依赖群主常在线转发，但连接数和逐对连接授权会增加。协议与体验评审阶段必须验证该拓扑适合目标网络与 20 人上限；若连接或授权体验不可接受，应在编码群组层前重新比较中心中继方案。中继方案会引入常在线主机、转发职责和额外的安全边界，不属于当前首版基线。

### 3.3 群组身份与成员变更

群组不能只靠显示名称识别。协议设计阶段需要明确：

- `groupId` 的生成与持久化方式，以及群创建者/管理者身份。
- 邀请信息的认证、接收方确认、重复邀请处理和过期策略。
- 成员加入、退出、移除及群信息变化如何形成有序、可验证的成员事件。
- 群组成员变更使用递增版本/epoch，消息需引用其所属版本；过期成员或不一致成员表的处理方式。
- 群组成员变更后，新成员能否看到加入前的历史消息。首版建议不补发离线期间内容，历史同步也不在首版范围内。
- 设备身份与用户可读昵称分离；昵称不能作为身份或授权依据。

建议在协议设计中采用创建者签署成员变更事件的权威模型，并明确创建者退出、失联或设备更换时的处理规则。具体规则须在协议冻结前确认。

## 4. 分阶段实施

### 阶段 0：需求与架构冻结

**工作**

- 确认 20 人群组人数包含本机用户，私聊上限为同时连接的 20 个不同设备。
- 确认全互联方案、逐设备连接同意、群主权限、群成员变更和群历史可见规则。
- 决定新客户端是否继续支持旧版 v3 私聊，以及新旧发现和协议选择规则。
- 定义消息投递、部分成功、拒收、离线和手动重发文案与行为。

**退出条件**

- 产品规则、容量基线和版本兼容矩阵经确认。
- 明确全互联连接/授权体验可接受；否则先调整拓扑，不进入协议实现。

### 阶段 1：公共协议与数据契约

**工作**

- 在公共文档中定义群组控制事件、成员列表版本、群消息信封、消息回执和错误状态。
- 确定协议版本策略；群组消息不得伪装成现有 v3 私聊消息。
- 为 JSON/二进制字段、UUID、指纹、枚举、长度、时序和去重规则提供跨语言样例与公共测试向量。
- 更新公共安全规则和 UI 规范；为 v3 单聊兼容（如纳入范围）增加明确的版本选择及降级防护规则。

**退出条件**

- C# 与 Swift 能独立编码/解码相同协议样例，非法字段和未知版本处理一致。
- 协议版本与旧版客户端互通边界已写清，不允许静默降级。

### 阶段 2：多连接管理核心

**工作**

- Windows 与 macOS 分别把单连接槽改为指纹索引的连接注册表。
- 实现同一对端重复连接检测/合并、连接竞争、统一取消、断线清理及连接上限保护。
- 每条连接独立维护读取循环、写入序列化、握手同意、文字回执及文件回执路由。
- 将发送、接收和错误状态绑定到连接与会话，而非全局单例属性。
- 确认更新安装/退出/窗口关闭期间所有连接的关闭与恢复行为。

**退出条件**

- 一台客户端可并发建立、保持和独立关闭多条连接；一条连接失败不影响其他连接。
- 同一设备不会因为私聊和群聊同时使用而建立重复连接。

### 阶段 3：20 路独立私聊

**工作**

- 改造两端会话列表与选择状态，允许多个私聊保持在线并互相切换。
- 每个私聊独立显示文字、图片和文件历史、草稿、回执、重试及连接状态。
- 发送动作明确绑定私聊会话与对端身份；窗口切换、后台回调和并发消息均不得串会话。
- 对 20 个不同对端连接建立和释放做资源及 UI 响应验证。

**退出条件**

- Windows 和 macOS 各自能同时维护 20 个独立私聊，消息与附件均不会串到其他会话。
- 新版与旧版私聊兼容行为符合阶段 0 定稿的矩阵。

### 阶段 4：群组生命周期与成员视图

**工作**

- 新增群组/成员本地持久化模型、创建群组、邀请、接受/拒绝、退出及成员移除操作。
- 成员邀请和变更事件经过已认证设备连接传输，并进行权限、签名/来源和版本检查。
- 建立群组连接：成员间按指纹连接，必要时逐对提示连接同意；群成员相同的连接与私聊复用。
- 增加群组列表、群信息/成员列表、在线状态和群会话时间线入口。

**退出条件**

- 两端对群 ID、成员集合和成员版本达成一致；不接受伪造、重复、过期或越权的成员变更。
- 20 人群组创建/加入/退出流程可完成，重复邀请与成员离开有明确结果。

### 阶段 5：群消息、图片与文件

**工作**

- 实现群文字消息扇出、成员回执、重复消息去重及部分送达汇总。
- 接入图片和文件；每个成员分别确认和接收，显示独立进度及失败原因。
- 实现仅针对失败成员的手动重发；已送达成员默认不重复接收。
- 成员离线、拒绝连接或文件拒收时，标记该成员未送达/拒收并继续发送其他成员。
- 文件重发前重新检查源文件；不承诺断点续传或 exactly-once 文件语义。

**退出条件**

- 群文字、图片、文件在不同成员上显示相同内容和发送者身份。
- 部分成员失败时其他成员仍可成功；UI 不误报全体送达。

### 阶段 6：跨平台联调与容量验收

**工作**

- 验证 Mac↔Mac、Windows↔Windows、Mac→Windows、Windows→Mac。
- 完成单独的 20 人群组场景、20 路私聊场景，以及两者成员完全不重叠时最多 39 条远端连接的组合场景。
- 验证多成员同时发消息、文字与文件并行、审批等待、断线、取消、拒绝、重复回执和部分成功。
- 验证群成员变更期间消息路由、成员表版本不一致、群创建者退出和应用重启后的本地状态恢复。
- 测量 CPU、内存、socket/句柄数量、发现与连接建立耗时、界面响应及消息完成率；据此确认 20/39 容量目标。
- 执行旧版协议兼容矩阵与不支持群聊时的清晰提示。

**退出条件**

- 两端共享向量一致，所有平台组合通过功能和安全负例。
- 20 人群和 39 个不同远端连接的容量目标通过；没有跨会话串消息、错误归属或虚假送达。
- 文档、UI 文案和实际实现一致，验收结果分别记录，不以单平台测试代替跨平台结论。

### 阶段 7：用户验收与合并

- 在 `dev/multi-user-conversations` 完成代码、必要测试、构建与跨平台验证。
- 汇总已实现范围、验证证据、未通过项和已知限制，提交用户检查。
- 用户确认可合并后再合并至主分支；不在验收前合并或创建发布包。

## 5. 跨平台实现分工原则

- 公共协议、数据契约、成员变更规则、安全边界和验收标准只在 `Project/Docs/Public/` 维护一份权威版本。
- Windows 实现位于 `Project/Windows/`，使用 C# / WinUI 3；macOS 实现位于 `Project/MacOS/`，使用 Swift / SwiftUI。
- 两端按公共向量独立实现，不共享运行时实现代码；公共测试向量和负例用于避免字段、编码及状态语义分叉。
- 先冻结共享协议，再并行开发两端的连接核心；群组端到端联调必须在两端核心都具备相同协议能力后进行。
- 平台特有 UI、文件系统、权限与通知按原生方式实现，但面向用户的产品状态保持一致。

## 6. 主要风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 全互联连接数及连接同意过多 | 20 人群最多每台 19 条群内连接；与 20 个不同私聊对象并存时最多 39 个远端连接 | 阶段 0 先确认拓扑和授权体验；阶段 6 做真实容量验证，失败时先重新评估拓扑 |
| 跨平台取消能力差异 | V4 通道不能参与安全取消，Windows↔macOS V5 取消及断线/重启完整矩阵尚未真实局域网验收 | V5 只在已认证通道上发送 recipient-bound abort；保持持久意图并等待目标以 V5 重连，提交后不允许撤销 |
| 群成员状态分叉 | 成员列表不同会导致消息投递到错误成员或旧成员继续收消息 | 成员变更事件认证、版本化、去重；过期 epoch 拒绝并提示同步/重连 |
| 并发读取/写入竞争 | 加密序列乱序、回执错配、消息串会话 | 每条连接单读循环和有序写入；按 ID 与设备指纹关联等待项 |
| 部分送达被误报 | 群内有人未收到但界面显示成功 | 存储每成员状态，汇总状态区分全部送达、部分送达和未送达 |
| 单成员拒收影响整群 | 现有拒绝行为会关闭当前连接 | 文件传输与连接绑定；拒收只终止对应成员上的文件流程，不中止其他成员投递 |
| 旧版互通不清楚 | 协议版本不一致时连接失败或发生危险降级 | 阶段 0/1 明确版本矩阵；禁止静默降级；群聊仅对具备新能力的客户端开放 |
| 无离线暂存造成内容缺失 | 离线成员看不到消息，发送方退出后不自动补投 | 明确未送达状态与手动重发；不显示排队成功或虚假送达 |

## 7. 暂不纳入首版

- 服务器中继、云端历史同步和离线消息收件箱。
- 群聊文件断点续传、群聊离线文件保管和自动补投。
- 群通话、已读回执、消息编辑/撤回、管理员角色细分、跨群转发。
- 群历史批量同步及新成员读取加入前消息。
- 超过 20 人的群组和自动扩容。

## 8. 待阶段 0 确认的问题

1. 20 人是否明确包含群创建者？本计划按包含计算。
2. 建群邀请是否需要每个被邀请成员逐个接受？本计划按需要接受处理。
