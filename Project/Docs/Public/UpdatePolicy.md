# 飞鸽快传应用更新规则

规则版本：1.0 · 整理日期：2026-10-24

本文件是 macOS 与 Windows 应用更新的共同规范，权威版本与两端源码统一在 `main` 主线上维护。本文规定后续实现与验收要求。当前状态（2026-10-29）：Windows 已发布 1.2.1 并完成应用内更新实测；macOS 0.4.0 的局域网更新来源与 P-256 信任根已配置，build 11 已发布到 Mac mini。本机 macOS 27 arm64 客户端完成 build 9 → 10 的完整升级验收，并从 build 10 → 11 更新后验证成功提示可关闭。macOS 尚无 GitHub 回退，Apple 公证、干净机器安装及 Mac mini 客户端验收未完成；Mac mini 当前为 macOS 12.7.6 Intel，低于应用最低系统版本 13.0。各端实际完成情况、测试结果和限制分别写入平台开发日志，跨平台摘要写入[更新日志](UpdateLog.md)。

## 1. 范围与基本原则

- 采用“后台检查 → 用户确认下载 → 完整验证 → 用户确认安装 → 安全退出 → 安装并重启”的流程。
- 自动检查、自动下载、自动安装是不同权限。首版仅默认开启自动检查，并在设置页说明会联网获取版本信息；自动下载和静默自动安装不默认启用。
- 更新不得打断正在进行的文字和文件收发，不得强制结束应用、强制重启系统或因检查失败阻止启动。
- 无互联网时，已有局域网发现、连接、聊天和文件传输照常可用。更新服务不是业务通信的前置依赖。
- 首版使用完整更新包。增量更新、灰度发布和自动回滚留作后续独立设计，不作为首版已经具备的能力。
- 现有不含更新功能的客户端，需手动安装一次带更新入口的新版本，后续才可应用内升级；始终保留手动下载安装的方式。

## 2. 版本、渠道与安装类型

| 概念 | 共同规则 |
| --- | --- |
| 产品版本 | 使用 `主版本.次版本.修订号`；平台可独立发版，macOS 与 Windows 的产品版本号无需相同 |
| 构建号 | 同一平台、架构和安装渠道下单调递增；每个正式发布的构建内容固定，不覆盖同名安装包 |
| 发布渠道 | 区分正式版与测试版；默认正式版，加入测试版需用户主动选择 |
| 安装类型 | Windows EXE、Windows MSIX、macOS 独立应用分别沿自身渠道升级，不在后台互相转换 |
| 架构 | 依据当前已安装应用的架构选择兼容包，同时校验系统支持情况；不因 ARM64 系统正在运行 x64 应用就自动切换安装架构 |
| 协议版本 | 与产品版本分别管理；是否互通以[通信协议](ProtocolOverview.md)及实际验收结果为准 |

比较版本必须解析数值和构建号，不按字符串排序。默认只安装当前平台、架构、渠道和安装类型下更新的构建；已安装的构建不再提示为新版，也不通过修改更新清单触发降级。测试版退出或手动回退涉及资料兼容性时，须另行说明操作与限制。

升级若改变通信协议或最低系统要求，更新说明必须明确受影响的系统、对端版本和行为。旧系统只获得仍兼容的更新；未兼容的对端显示原因，不自动降级通信协议，也不远程触发对方安装更新。

## 3. 设置入口与检查策略

设置页增加“版本与更新”，至少显示当前产品版本、构建号、发布渠道、“检查更新”按钮、自动检查开关和最近检查结果。macOS 应用菜单可提供同名入口，两个入口共用检查状态。

- 自动检查：应用启动并完成初始化后在后台执行，不阻塞设备身份准备或主界面；正常情况下最多每 24 小时检查一次，长时间后台运行时也遵守此间隔。
- 首次安装时，先完成[首次引导](FirstRunOnboarding.md)中的更新偏好保存，待用户结束引导后再安排首次自动检查；不能在欢迎页提前联网或在系统授权弹窗之上提示更新。
- 用户关闭自动检查后，停止后续自动请求；手动“检查更新”仍可使用。开关须先持久化成功再更新界面。
- 手动检查可以立即触发；已有请求进行时复用该请求，不能重复启动检查或下载。
- 自动检查失败保持安静，在设置页记录结果；失败后的自动重试同样遵守至少 24 小时间隔，连续失败可进一步延长间隔，避免反复联网。手动检查失败则展示可理解的原因和重试入口。
- 必须区分“已是最新版本”“检查失败”“当前系统暂无兼容更新”。网络错误、无效清单和签名错误不能显示为“已是最新版本”。
- 自动检查只请求版本和兼容性所需的信息，不发送设备私钥、设备指纹、设备名称、局域网地址、聊天记录、文件内容或接收路径。不额外生成用户追踪标识。

## 4. 提示、下载与安装交互

| 状态 | 必须提供的反馈或操作 |
| --- | --- |
| 发现新版 | 版本、发布时间、下载大小、更新摘要；“下载更新”“稍后”“跳过此版本” |
| 下载中 | 已下载大小、总大小和真实进度；可取消，失败可重试；不能显示模拟成功 |
| 验证中 | 明确正在验证，验证完成前不可安装 |
| 可以安装 | “安装并重启”“稍后”；用户需明确确认安装 |
| 有活动收发 | 提示等待收发结束，提供“收发完成后安装”“稍后”；不得主动中断业务 |
| 等待安装 | 显示正在等待收发结束，允许取消等待 |
| 安装失败 | 给出可执行的重试或手动安装入口，保留用户资料；不显示更新完成 |

“稍后”结束本次自动提示，设置页仍能查看更新；同一构建的自动提示一天最多一次。“跳过此版本”按平台、渠道和构建号持久化，新构建可重新提示，手动检查仍可查看被跳过的版本。

下载请求确认不等于安装确认。“收发完成后安装”是对本次已验证构建的明确安装授权，仅在本次应用运行期间有效；取消等待、退出或重新启动后，不得凭旧授权自行安装。安全修复可以突出标记，但首版不强制升级、不禁用旧版应用。

首版取消或中断下载后允许重新完整下载，不承诺断点续传；只在临时文件完整下载且验证通过后标记“可以安装”。缓存清理只操作更新专用目录，不清理用户接收文件或聊天附件。

## 5. 安装前的收发保护与退出

1. 用户确认安装后，先检查当前发送、接收、已接受的队列以及尚未处理完成的文字消息；仅存在空闲长连接不应无限阻止更新。
2. 有未完成工作时保持原收发流程。若用户选择“收发完成后安装”，继续接收业务，待工作自然结束后才尝试进入更新阶段；持续有业务时继续等待，用户可取消等待。
3. 进入更新阶段时，原子地关闭新业务入口，包括新连接、发送和接收新批次，再复核活动工作，消除“检查空闲后又收到新任务”的竞争。出现活动工作则退回等待，不丢弃已接受内容；对端请求按既有协议拒绝或断开，不能伪造成功回执。
4. 保存设置、草稿和会话记录，确认已完成消息与文件的落盘工作结束。保存失败则留在当前版本并显示原因，不带着未保存资料退出。
5. 正常关闭连接并清理后台服务，真正退出主进程。关闭主窗口后仍后台运行，不等于满足安装条件；安装器不得强杀应用来绕过退出失败。
6. 确认旧进程退出、更新包仍有效后开始安装；交接失败或安装取消应允许重新打开原版本。新版本启动后核对实际版本、读取原资料并记录结果，不能仅凭安装器已启动就报告成功。

更新后重启重新执行正常身份预检与连接授权。设备身份保持原值，但不恢复上一条连接的用户同意，也不自动重新发送失败或未确认的消息。

## 6. 平台安装方案

| 平台 | 首选方案 | 实现边界 |
| --- | --- | --- |
| Windows EXE | 应用下载并验证安装包，安全退出后调用现有 Inno Setup 安装器覆盖安装 | 保持安装标识、安装范围和资料目录稳定；由安装器或独立交接进程完成旧进程等待、结果处理和重开；继续按当前用户安装，不无故请求管理员权限 |
| macOS 独立应用 | 首版为项目自有更新器（不引入 Sparkle 2），流程与安全要求不变 | 已实现签名清单验签、用户确认下载、大小/SHA-256 校验、收发空闲衔接、代码签名校验与同目录原子替换。不再依赖第三方框架的 appcast；清单格式、信任根与签名算法见 [macOS 客户端说明](../../MacOS/README.md)。保持应用标识、钥匙串访问约定和资料目录稳定；处理应用位置不可写、磁盘空间不足等失败 |
| Windows MSIX | 若继续维护该渠道，使用 App Installer 或对应发行渠道的更新机制 | 不直接替换包内文件，不调用 EXE 安装器转换；配置不得阻止旧版启动或强制关闭收发；须验证系统更新时机满足本文要求后再开放该渠道自动更新 |

平台更新框架可使用原生对话框，但安装确认、收发保护、状态含义和失败处理必须遵循本文。覆盖安装不自动等于事务式替换或自动回滚，不能据此承诺零失败或无条件恢复旧程序。

## 7. 更新发布信息与托管

先采用固定 HTTPS 更新入口与静态发布文件，安装包可由对象存储或 CDN 分发，无需先建设动态服务。域名、托管提供方和平台文件格式在接入时确定，不把示例地址写成可用生产地址。

双平台共享发布字段语义，线上格式与签名算法按平台选择：macOS 当前使用项目自有签名 JSON 清单（P-256 ECDSA/SHA-256，客户端 CryptoKit 验签），Windows 使用 RSA-PSS 签名清单。从同一发布记录导出各端信息，避免人工维护后版本、摘要和下载地址不一致；Windows RSA 密钥不能签发 macOS 清单。

每个发布条目至少包含以下内容；平台框架已表达的字段沿用原生格式。

| 字段组 | 必须表达的信息 |
| --- | --- |
| 格式 | 清单格式版本或框架版本约定；不支持的必要字段和格式必须拒绝 |
| 目标 | 平台、架构、发布渠道、安装类型 |
| 版本 | 产品版本、构建号、发布时间 |
| 系统 | 最低系统版本及其他安装兼容条件 |
| 说明 | 更新摘要、完整说明地址，以及已知限制 |
| 下载 | 固定版本下载地址、文件大小、SHA-256、更新包签名或框架对应的签名信息 |
| 互通 | 支持的通信协议版本及对端升级要求；描述必须与已验收能力一致 |

Windows 清单使用 RSA-PSS 签名原始 payload 字节，并严格验证来源、重定向、固定 Host 和内容完整性。客户端不内置 GitHub 访问令牌。Windows 当前局域网更新端点、部署与验收状态见 [Windows 更新服务文档](../Windows/UpdateService.md)。日期统一使用带时区的 ISO 8601 表示，界面可转成本地时间。

## 8. 信任与下载校验

- 更新入口、说明与安装包使用 HTTPS，拒绝证书错误和降级到 HTTP。下载及重定向目标须满足客户端配置的可信域名和协议规则，不接受局域网发现消息或对端聊天消息指定更新来源。
- SHA-256 用于完整性检查，不能单独证明发布者身份。Windows 更新清单须验证发布签名，公钥随应用内置；签名应覆盖目标、版本、下载地址、大小和摘要等关键字段，验证后再采用其内容。
- Windows 正式安装包及主程序使用可信代码签名；安装前校验签名、可信链与预期发布者。测试包不进入正式更新渠道，不提供“忽略验证继续安装”。
- macOS 首版使用项目自有签名清单（P-256 ECDSA/SHA-256 或 Ed25519，公钥随应用内置），正式应用使用 Developer ID 签名并公证；签名须覆盖目标、版本、下载地址、大小和摘要等关键字段，安装前再次校验新旧应用的代码签名，不能只验证下载摘要后自行替换应用。若后续改用 Sparkle 2，须同时满足其 EdDSA 与 appcast 验证要求。
- 下载完成须复核大小、摘要、签名和目标兼容性，安装前保证交接的是同一份已验证文件。任何验证失败均停止安装，保留当前版本并提示重试或从正式入口手动下载。
- 发布签名密钥与设备通信身份密钥分开管理。私钥不进入仓库、安装包、公开托管或 `Release/`；在受控签名环境保存。密钥轮换须先提供旧客户端可验证的信任迁移路径，不能仅用远端清单替换可信公钥。
- 不承诺仅凭缓存构建号就能完全防止旧清单重放；首版至少拒绝比已安装构建更旧的更新，并记住已验证见过的最高发布构建。更严格的清单过期和撤回机制须单独设计并验收。

## 9. 资料、迁移与失败恢复

- 保留设备身份与指纹、设备名称、设置、接收目录、草稿、聊天及传输记录、已接收文件。正常升级不重新生成身份，不因资料读取失败就初始化为空资料。
- 安装目录与资料目录保持分离；覆盖安装和卸载继续遵守平台既有资料保留约定。跨安装类型迁移不属于常规更新，需独立设计和用户明确选择。
- 资料格式变化必须有独立格式版本、来源版本范围和迁移步骤。迁移前备份受影响的本机资料，成功校验后提交；备份涉及聊天等内容，应保持原有访问保护，不上传更新服务。
- 无需复制全部接收文件作为迁移备份。备份空间不足、权限不足或迁移失败时，停止写入并保留原资料与可恢复副本，显示可操作错误。
- 老版本不一定能读取新资料，手动降级前必须验证兼容性或恢复相匹配的备份；不能承诺重新安装旧包就一定恢复正常。
- 下载或验证失败不得修改已安装程序。安装失败按平台实际能力保留或恢复可运行版本；无法自动恢复时提供正式安装包入口和资料位置说明，不能声称已有自动回滚。
- 撤回有问题的发布后停止向新检查请求推荐它；已下载或已进入安装流程的副本不一定能被实时拦截，不能承诺远程即时撤回。修复以更高构建号发布，避免覆盖旧包或靠清单降级。
- 更新诊断日志只记录版本、阶段、时间和经脱敏的错误码，不记录消息、文件内容、密钥或敏感完整路径。

## 10. 开发、打包与发布顺序

1. 先修改代码与必要的开发文档，完成构建、测试或运行验证，报告结果供用户确认；默认不生成安装包或其他交付包。验证所需临时构建不视为交付打包。
2. 用户确认并明确要求打包后，才生成交付包。此为开发发布流程，与终端用户的更新确认分别处理，不能相互替代。
3. macOS 与 Windows 所有交付包及随包校验文件、说明、依赖和发布用更新清单，统一输出或汇总到仓库根目录同级的大写 `Release/`，可按平台、版本、架构分目录；脚本以仓库根目录定位，不依赖当前工作目录。生成内容不提交 Git；源脚本、模板和规则文档可提交。
4. 正式构建输入使用仓库内源资源，不从被忽略的 `Release/` 取材。两端沿用已确认的 v1 图标，正式源资源位于 `Project/Ui/Branding/FeigeIconV1/`；Windows ICO 与 MSIX PNG 使用同一母图，macOS 在签名前复制 `Feige.icns` 并设置 `CFBundleIconFile`。变更图标设计须先经用户确认。
5. 对最终字节执行签名、摘要生成与验收。macOS 应用先完成资源写入、签名和公证，再生成更新归档及其更新签名；Windows 安装包完成代码签名后再计算摘要、生成并签署清单。之后不得修改受签名和摘要覆盖的内容。
6. 先上传不可变的版本包与说明，核验远端文件和下载结果，再最后切换更新入口，避免客户端先看见清单却下载不到文件。是否对外发布须按本次用户授权执行，不能将“要求打包”自行解释为“要求公开上线”。
7. 保留必要的历史版本和校验记录，记录包版本、构建号、来源平台提交、互通范围与已知限制。版本 tag 与跨平台发布摘要均维护在统一 `main` 主线上。

## 11. 首版验收清单

以下为待实现功能的验收要求，不是已完成测试记录。两端分别记录实测系统、架构、安装渠道和结果，未覆盖项明确标注。

- [ ] 检查成功、无兼容更新、网络失败、关闭自动检查、手动检查、重复点击、稍后与跳过构建。
- [ ] 正式版/测试版隔离，数值版本比较，同版本新构建、旧构建拒绝、系统与架构不兼容、EXE/MSIX 不混用。
- [ ] 慢速下载、中断、取消重试、磁盘不足、大小/摘要错误、清单或包签名错误、发布者错误、HTTP 或非法重定向。
- [ ] 空闲连接不阻塞更新；双向文件、排队附件与文字待回执时不被打断；等待可取消，临界时刻的新请求不会丢失或伪成功。
- [ ] 下载完成后不擅自安装；保存失败不退出；关闭窗口仍后台运行时能正确交接；旧进程未退出时不强杀和覆盖。
- [ ] 用正式或测试用受信任链走完整“旧版 → 新版”流程；安装取消、交接失败、安装失败、重启失败均有真实反馈。
- [ ] 带真实身份、设置、草稿和聊天记录升级后逐项验证保留，已接收文件不变；资料迁移失败保留原件，未知格式不清空。
- [ ] 更新后实际运行版本正确，重新完成身份预检与连接同意；断网仍可局域网收发；浅深色、高 DPI 与长更新说明可用。
- [ ] 包上传后从正式候选地址重新下载验证；发布清单最后切换；首次手动升级入口可用；未把测试签名包标为正式发行。

## 12. 实施顺序与参考

建议先完成更新服务抽象、设置入口和签名清单校验，再实现下载、收发空闲协调、平台安装交接及端到端验收。签名密钥、可信发布者、托管地址、精确清单格式与构建号来源，须在开放真实更新下载前配置并完成验证；未就绪的入口应明确显示未配置。
