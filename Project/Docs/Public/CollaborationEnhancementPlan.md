# 跨网段、常驻联系人与离线待发开发计划

2026-11-03 起草。本计划落实与内网通 3.4.3055 对比后确定要做的五项能力，Windows 与 macOS 同步实现。协议细节见[通信协议 v6](ProtocolV6.md)；与本计划冲突的旧规则已在[开发总则](DevelopmentRules.md)和[多人会话开发计划](MultiUserConversationPlan.md)中同步修改。

## 1. 范围

| 序号 | 能力 | 一句话说明 | 协议影响 |
| --- | --- | --- | --- |
| 1 | 跨网段连通 | 用户保存对方网段或地址，本机用单播探测找到设备 | 新增未认证 UDP 探测，TCP 协议不变 |
| 2 | 未读与通知 | 会话未读数、托盘/菜单栏入口、新消息系统通知 | 无 |
| 3 | 常驻联系人 | 同意过且被标记的设备上线后自动重连，可随时撤销 | 无，改变“每次重连都询问”的产品规则 |
| 4 | 文件夹与断点续传 | 一对一发送文件夹，中断后从已收字节继续 | 新增 v6 |
| 5 | 离线待发队列 | 对方离线时发送方本机排队，连上后自动投递 | 无，改变“不做离线投递”的产品规则 |

明确不做：一键关闭防火墙、盲扫公网或未经用户配置的网段、与飞鸽/飞秋互通、隐藏本机 IP、广告/积分/商城/邮件感知/应用中心、远程协助、服务器中继。群聊的离线投递和断点续传不在本期范围，群行为保持 v4/v5 不变。

## 2. 跨网段连通

mDNS 不跨路由，所以需要用户明确给出网段。单播探测只回答“这个地址上是否有飞鸽、它的 TCP 端口是什么”，结果与 mDNS TXT 一样不可信，身份仍由握手确认。

- **用户配置**：设置页“其他网段”，每项是单个地址（`192.168.60.12`）或前缀（`192.168.60.0/24`）。只接受私网 IPv4（10/8、172.16/12、192.168.0.0/16、169.254/16），前缀长度 24–32，最多 16 项（合计不超过 4096 个地址）。
- **探测**：启动、网络变化、手动刷新时立即扫一轮，之后每 60 秒一轮；每秒最多 50 个地址。连续 3 轮无应答的设备从列表移除。
- **应答开关**：设置项“允许其他网段发现本机”，默认开启。关闭后仍可向外探测，但不应答；mDNS 不受影响。
- **防护**：只响应私网来源；应答不大于请求（请求固定填充到 512 字节），无法放大；全局限速每秒 100 次应答；UDP 端口绑定失败时只降级为不可应答，并在设置页说明。
- **合并**：探测结果按指纹与 mDNS 结果合并，同一设备只显示一行；mDNS 与探测同时存在时优先 mDNS 地址。
- **防火墙**：固定端口 `52526/UDP`。帮助文案只说明需要放行，绝不替用户关闭防火墙。
- **后续（本期不做）**：连入连接带来的反向地址学习。

## 3. 未读与通知

- 只在本机计数，不发已读回执。收到文字、完成接收的图片/文件计入未读；当前打开且窗口处于激活状态的会话不计入。
- 打开会话或窗口重新激活到该会话时清零。未读随会话记录持久化，重启不丢。
- 私聊和群聊都计入，群聊只计其他成员的消息。删除或隐藏会话后不再计入总数。
- macOS：Dock 角标显示总未读，`MenuBarExtra` 提供未读数、显示主窗口和退出。Windows：系统托盘图标，提示文字含未读数，左键显示窗口，右键菜单含显示与退出。
- 通知沿用现有开关。窗口未激活时新消息弹系统通知，内容为发送方与摘要；文件显示文件名。关闭通知后未读数仍然更新。

## 4. 常驻联系人

- **建立**：连接确认框增加“以后自动同意这台设备”；会话菜单增加“设为常驻联系人 / 取消常驻联系人”。只有已通过握手认证的设备才能设为常驻。
- **绑定**：以完整 SHA-256 指纹为准，不看名称、地址或 mDNS 内容。信任是单向的本机设置，不同步给对方。
- **自动同意**：入站连接握手认证后，指纹在常驻名单内则直接同意，并写一条本机日志；**不影响逐个文件的接收确认**。
- **自动重连**：常驻联系人出现在设备列表且未连接时自动发起直连。指纹字典序较小的一方立即发起，另一方等 10 秒，以减少同时拨号。
- **退避**：被拒绝后本次运行不再自动拨该设备，手动连接会解除；超时或网络失败按 30 秒、1、5、30 分钟退避。对方未把本机设为常驻时，对方会看到普通确认框。
- **撤销**：取消后立即从名单移除，已建立的连接保持到断开；设置页列出全部常驻联系人并可移除。
- **上限**：自动连接与手动连接共用 20 台直连上限，达到上限时不再自动拨号。

## 5. 文件夹与断点续传

- 只用于双方都支持 v6 的一对一连接。对方版本较低时，单文件照常发送但不能续传，发送文件夹时明确提示“对方版本不支持”。
- 文件夹在接收方只询问一次，确认框显示文件夹名、文件数和总大小。会话里是一条消息，进度按总字节聚合。
- 发送方递归枚举常规文件：不跟随符号链接，跳过 `.DS_Store`、`Thumbs.db`，不发送空目录。单次上限 10000 个文件、32 层、相对路径 1024 字节。
- 接收方写入 `接收目录/文件夹名/…`，目录已存在时用 `文件夹名 (1)`，绝不合并到已有目录，也绝不覆盖文件。
- 断线后保留 `.part`，同一文件内容再次发送时从已收字节继续；完整 SHA-256 不符时删除未完成文件，下次从 0 开始。未完成文件 7 天后在启动时清理。
- 文件大小或修改时间变化视为新文件，不续传旧数据。
- 群聊文件不支持文件夹和续传。

## 6. 离线待发队列

- 只用于私聊。对方未连接时输入框和附件入口仍可用，消息状态为“待发送”，内容保存在发送方本机，没有服务器，也不经第三台设备。
- 连接建立后按时间顺序自动投递：文字沿用原消息 ID，对端按 ID 去重；文件发送前重新检查源文件是否存在，不存在则标记失败并说明原因。
- 应用重启后待发内容保留，不再标记为失败。投递中断的消息回到待发，下次连接继续。
- 待发内容不会单独发起连接请求，避免反复打扰非常驻联系人：常驻联系人按第 4 节自动连接后投递；其他设备在任一方手动连接后投递。连接被拒绝时保留待发。
- 用户可以取消任一待发消息。每个会话最多 200 条待发，超过 7 天未投递转为失败并提示手动重发；启动时和运行中每小时检查一次过期。
- 文件接收确认不变：对方拒绝即终止该文件，不再重试。
- 存储：消息记录增加可选字段 `outboxSince`（Mac `ChatMessage.outboxSince`，Windows `ConversationMessage.OutboxSince`，为空时不写出，旧版本读取时忽略）。带此字段且状态为“排队/发送中”的已发送消息即为待发；中断、断线或重启时回到“排队”，其他未完成消息仍转为失败。
- 投递：连接安装后、每条投递结束后各取一次该会话最早的待发消息，逐条发送；有待发时新消息也排在其后。
- 线格式不变，不新增协议版本：文字仍用原消息 ID 的 `text` 记录，文件仍走既有清单与接收确认。

## 7. 实现顺序与验收

顺序：跨网段 → 未读与通知 → 常驻联系人 → 文件夹与断点续传 → 离线待发。

| 能力 | 自动化验收 | 实机验收 |
| --- | --- | --- |
| 跨网段 | 配置解析边界、探测报文编解码、回环探测、私网来源过滤、放大防护 | 两个真实网段互相发现并连接 |
| 未读与通知 | 计数、清零、持久化、活动会话不计入 | Dock/托盘、系统通知 |
| 常驻联系人 | 自动同意仅匹配完整指纹、撤销、退避、不绕过文件确认 | 双方重启后自动恢复连接 |
| v6 | 共享握手向量；续传、哈希不符、路径穿越、符号链接、超额声明、不覆盖 | Mac↔Windows 中断后续传、文件夹互发 |
| 离线待发 | 重启保留、顺序、去重、源文件缺失、取消、过期 | 对方上线后自动投递 |

没有在两台真实设备上验证的能力，不得在发布说明中写成“已验收”。
